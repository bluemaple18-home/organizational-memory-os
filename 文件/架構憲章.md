# 架構憲章

本文件定義 Organizational Memory OS 不可被 implementation convenience、donor framework、AI Core priority 或單一 runtime 改寫的核心契約。

## 一、六個 Truth Boundary

### 1. 證據 Truth

`Raw Evidence != Derived Interpretation != Knowledge`

Outlook、Teams、Slack、Jira、Git、文件、Agent 輸出、LLM 摘要、Automation 結果先是 Evidence。Evidence identity 與 provenance 必須可追溯；Knowledge 不能反寫原始 Evidence。

### 2. Knowledge Truth

`Candidate != Canonical`

Extractor、Reviewer AI、人、Agent、Importer 都只能產生 Candidate 或 Mutation Proposal；不得直接取得 Canonical write authority。

### 3. Permission Truth

`Permission-before-Retrieval`

流程固定：Identity → Role/Group → Knowledge Scope → Capability → Authorized Retrieval Space → Vector/Graph/Keyword Retrieval → Context → LLM。

模型不是權限 enforcement boundary。

### 4. Verification Truth

`Required Verification != Actual Verification`

驗證狀態至少保留：`PASS / FAIL / PARTIAL / NOT_RUN / STATIC_ONLY`。缺驗證不得視為通過；部分執行不得 aggregate 成 PASS。

### 5. Acceptance Truth

`EXECUTED != VERIFIED != ACCEPTED`

Agent 做完、Evaluation 跑完、Reviewer 批准是三件不同的事。Acceptance 狀態至少：`PENDING / ACCEPTED / REJECTED / BLOCKED`。

### 6. Mutation Truth

`Proposal != Canonical Write`

只有滿足 Permission、Verification、Acceptance 的 Proposal 才能進 Canonical Knowledge Writer。Canonical resource 採 Single Authoritative Writer。

## 二、Knowledge 與 Procedure / Skill 分離

Knowledge = 知道什麼。

Procedure / Skill = 遇到問題時怎麼做。

保留：Evidence → Knowledge → Repeated Successful Pattern → Skill Candidate → Validation → Review → Published Skill。

Skill 可吸成熟格式中的 trigger、inputs、procedure、verification、failure path、references/assets；但 owner、permission、provenance、lifecycle、version、approval authority 由本產品掌握。

## 三、AI Core 邊界

AI Core 是 Agent Governance / Execution / Runtime / Receipt donor。

Knowledge SaaS 是 Organizational Knowledge / Evidence Ingestion / Permission / Retrieval / Review / Lifecycle / Delivery authority。

雙向整合：

```text
AI Core Execution → Receipt/Evidence → Knowledge SaaS Candidate → Review → Knowledge
Knowledge SaaS → Permission-aware bounded context → AI Core Task
```

不得形成兩套 canonical truth。

## 四、Prior-Art First

新增重要能力前必須經：Problem → Existing Seam → Prior Art Scan → Semantic/Authority Diff → Tests/Failure Cases → Algorithm/Adapter Reuse → 必要時 Dependency → 最後才 Custom Code。

正式原則：

> 借工程、保架構。

優先吸收 failure cases、regression tests、algorithm、protocol pattern、adapter、operational handling；慎重吸 dependency、storage、schema；禁止搬 canonical authority、identity、permission authority、lifecycle/FSM、task model、memory truth、knowledge truth、mutable runtime DB 當 canonical DB。

## 五、共享研究但產品優先級獨立

AI Core 的單人資源、token、parked priority 不構成本產品 constraint。

正式原則：

> Shared Research, Independent Product Priority.

每個共享能力需獨立評估 Knowledge SaaS 的安全、產品、治理、成本、規模與商業價值。
