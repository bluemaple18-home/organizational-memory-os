# 待辦重整

## 一、狀態標籤

重要 Backlog item 以以下狀態標記：

- `ALREADY_EXISTS`：現有架構/元件已涵蓋，不重做
- `PARTIAL`：方向已有但 contract / implementation 不完整
- `MISSING`：真正缺口
- `DONOR_AVAILABLE`：已有成熟先例或可吸收實作
- `CUSTOM_CODE_REQUIRED`：仍需自研產品獨有語意
- `SHOULD_NOT_ADOPT`：明確不應搬進本產品

本輪 Minimal Core Rebaseline 再增加責任分類：

- `DOMAIN_CORE`：產品/domain responsibility，架構必須保留
- `EXECUTOR_ONLY`：Agent / Model / Worker 只是可替換 executor
- `DETERMINISTIC_FIRST`：優先 deterministic code / rule / parser / validator
- `MODEL_ASSISTED`：只有語意問題才使用模型
- `RUNTIME_OWNED`：交既有 runtime / worker / queue / provider，不成為 Knowledge subsystem
- `PROJECTION_ONLY`：可重建衍生物，不能取得 canonical authority
- `ENTERPRISE_GOVERNANCE`：企業安全/治理核心，不因 Agent 瘦身而降級
- `DEFER`：現在不施工
- `REJECT`：目前不應引入

## 三、Agent / Worker Audit 問題

所有現有 Agent / Worker / Reviewer 卡必須回答：

1. Product/domain responsibility 是什麼？
2. 為什麼 Knowledge OS 必須擁有？
3. Agent 是否只是 executor？
4. 是否可以 deterministic？
5. 是否有成熟 OSS / API / SDK 可直接用？
6. 是否真的需要 canonical storage？
7. 是否只是 rebuildable projection？
8. 是否真的需要獨立 lifecycle / DB / registry / ledger / FSM？
9. 如果移除 Agent 名稱，產品 capability 是否仍成立？
10. Phase-1 內部導入是否必要？
11. Future SaaS 是否必要？
12. 現在是否應施工？

## 五、高 token 研究卡改寫原則

能找到成熟 donor 的研究卡，改成 teardown / adaptation card：

- Context Budget：拆 Codex / GraphRAG engineering，只自研 ContextPolicy
- Telemetry：採 OpenTelemetry GenAI conventions，只做 mapping
- 文件解析：MarkItDown / Docling / Unstructured / Tika，不自造 parser
- Permission Engine：OpenFGA / OPA / Cerbos 做 semantic diff，不自造 graph evaluator
- Work Grouper：OpenChronicle / DayTrail / OCEL，不自造 sessionization
- Source Adapter：官方 API / SDK → configure → wrap → adapt → 最後才 custom
