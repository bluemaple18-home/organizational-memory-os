# 權限、政策與設定治理

## Permission-before-Retrieval

正式流程：

```text
User Identity
  ↓
Role / Team / Group
  ↓
Knowledge Scope
  ↓
Capability
  ↓
Authorized Retrieval Space
  ↓
Vector / Graph / Keyword Retrieval
  ↓
Context
  ↓
LLM
```

禁止：先全公司搜尋、把機密內容塞進 Context，再叫模型不要說。

## Capability

至少考慮：`discover / retrieve / answer-with / view-source / upload / propose-change / approve / publish / export / admin`。

## Atom-level permission

已原子化的 Knowledge Atom 必須有自己的 access metadata，不能只靠文件 ACL。可包含：tenant、team、role、user、client/project、sensitivity、sharing policy、source ACL snapshot。

## Source ACL inheritance

Source ACL → Evidence ACL → Candidate Scope → Canonical Permission。

萃取不得自動放寬權限；放寬需要明確 authority。

## Managed Policy Floor

設定層級：

```text
Platform
→ Organization
→ Tenant
→ Department
→ Team
→ User
```

必要時另有 Client / Project / Workspace。

安全型設定採：**lower scope may restrict but cannot expand authority**。

例：Company `external_ai=DENY`，Department 不得改成 ALLOW；Company export=ALLOW，Department 可改 DENY。

## Config Scope / Precedence

每個 effective value 要能回答：

- authority
- allowed scopes
- merge semantics
- override direction
- managed lock
- effective value
- source
- decision trace

## External Capability Admission

企業 connector / MCP / internal API 應經：

```text
Source
→ Identity
→ Trust / Origin
→ Declared Capability
→ Requested Permission
→ Tenant Policy
→ Admission
→ Enabled Adapter
```

不要因 AI Core consumer 少就延後這個企業能力。

## Prior Art

- OpenFGA：fine-grained authorization engine、ListObjects / Check、RAG pre-filter pattern
- OPA：policy-as-code / tests
- Cerbos：resource policy / query-plan pattern

產品自己保留 Organizational Permission Model；第三方 engine 不能成為 canonical permission authority。
