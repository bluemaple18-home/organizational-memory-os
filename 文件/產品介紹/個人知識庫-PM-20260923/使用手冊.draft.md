# 個人知識庫｜PM 使用手冊

適用範圍：目前的 Personal Memory 小專案。編寫日期：2026-09-23。這是可供內部介紹與試用的文件初稿；不代表新增功能已上線。

## 1. 這個產品幫你做什麼

把你選定的工作紀錄保存到本機，保留來源與候選內容，並用每週回顧確認哪些內容值得保留、哪些改變了、哪些需要找人補充。適合放需求決策、會議結論、問題排查與例外處理紀錄。

現階段主要完成「手動匯入 → 收件匣 → 每週回顧 → 分類收尾 → 歷史追蹤」。完整的自動知識萃取、語意搜尋、圖形介面與公司共享送審，不能當成本版已提供的功能。

## 2. 先分清楚四種東西

| 名稱 | PM 可以怎麼理解 |
| --- | --- |
| 來源快照（Evidence） | 匯入時保存的檔案內容與來源資訊，讓之後有依據可查。 |
| 候選紀錄（Candidate） | 待判讀的材料；匯入成功時是 PROPOSED，還不是正式知識。 |
| 本期回顧清單（Review Queue） | 系統依候選紀錄及回顧紀錄計算出的待處理清單。 |
| 回顧歷史（Review History） | 每週是否有收尾、是否漏做；不是公司知識發布紀錄。 |

目前 `review done` 會記成 `NO_PROMOTION`：意思是這期已完成分類收尾，但沒有把候選升格成正式記憶，也沒有送到公司知識庫。這個狀態不是「操作失敗」。

## 3. 第一次使用：請研發協助完成

目前交付的 Host 整合是 **Claude Code 與 Codex**，另有本機命令列；安裝一次兩邊都會接上。唯一差別是 **Codex 第一次啟動時，要由使用者本人批准 SessionStart hook trust**——這一步不能由安裝程式代勞，未批准時 `doctor` 會明確標 WARN，不會假裝正常。現行提醒機制使用 macOS；裝置與 Ruby 相容性由交付包及 `doctor` 檢查。

先取得管理者提供的產品包、你的 owner 身分及 tenant 值。以下範例在解壓後的產品目錄執行；`PM` 只是一個方便輸入的 shell 變數，沒有修改系統 PATH。

```sh
PM="./exe/omos-personal-memory"
```

研發若在本 repository 根目錄操作，則使用：

```sh
PM="./product/personal-memory/exe/omos-personal-memory"
```

由研發將下列兩個值換成管理者提供的實值，再執行安裝。不要複製別人的身分，也不要把示例值拿來處理真實工作資料。

```sh
PM_OWNER="管理者提供的完整員工 URN"
PM_TENANT="管理者提供的 tenant 值"
"$PM" install --owner "$PM_OWNER" --tenant "$PM_TENANT"
"$PM" doctor
"$PM" status
```

確認安裝成功、健康檢查沒有 FAIL，再開始匯入。WARN 需由研發判讀，不能直接等同失敗或全部忽略。安裝設定與之後的資料匯入是兩個步驟；本手冊的製作沒有代你安裝或更動 Host。

預設資料庫位於 `~/.omos/personal-memory/personal.db`。來源快照檔與資料庫都屬於個人保存範圍；備份時請研發確認完整 Store，而不是只拷貝正在使用中的一個 SQLite 檔。

## 4. 每天：存下一份有用的工作紀錄

### 步驟 A：準備 .md 或 .txt

目前直接匯入支援 UTF-8 的 `.md`／`.txt`。PDF、Word、圖片、聊天平台連結不是這個匯入口已支援的格式。請先人工整理成文字，並保留原始來源連結或檔案位置。

建議一份紀錄聚焦一件事。以下是教學用的虛構範例，不是真實產品決策：

```text
主題：訂單查詢頁的預設篩選
日期：2026-09-23
專案／任務：PM-DEMO-01（教學示例）
背景：同事需要快速確認近期的訂單。
決定：預設顯示最近 7 天，仍可手動改期間。
理由：先縮小查詢範圍，避免一開始就列出太多資料。
適用限制：尚未處理跨月份報表需求。
來源：本次討論紀錄／原始文件位置。
待確認：客服是否需要不同的預設值。
```

來源連結是你提供的追溯線索；匯入 `.md` 不代表系統已連線抓取或驗證該連結。

### 步驟 B：選擇記憶類型、匯入，再確認收件匣

匯入時必須指定 `--memory-kind`，才能建立候選。需求決策可用 `DECISION`；經驗教訓用 `LESSON`；操作程序用 `PROCEDURE`；專案背景用 `PROJECT_CONTEXT`。這是資料類型，與每週回顧的 `UNSEEN` 等比較分類是不同的欄位。

```sh
"$PM" import "需求決策.md" --memory-kind DECISION
"$PM" inbox list
```

成功時會顯示 `CANDIDATE_PROPOSED`，以及 evidence、SHA-256、完整 candidate 識別碼。請確認這次的來源、內容與身分正確，並保留完整 candidate 識別碼，之後分類收尾會用到。

若看到 `NEEDS_CANDIDATE_INPUT`，代表來源快照已保留，但還沒有候選。補上 `--memory-kind DECISION` 等適當類型，用同一來源重新執行即可；不要把程式沒有報錯當成候選已建立。候選目前使用原文前 800 字元的摘錄，完整來源另存快照；不是自動摘要，也不是只剩這段摘錄。

同一來源、同一身分且內容相同的檔案重匯，應回報重放，不會多生一份候選。相同內容但來源或身分不同，不等於合法重放；遇到來源衝突應交研發確認，不能改身分硬塞。

匯入成功只表示材料已保存成候選；系統沒有因此宣稱已驗證內容真實，也沒有自動摘要或發布。

## 5. 每週：回顧、分類、確認收尾

### 步驟 A：看本期與漏做的週

```sh
"$PM" review due
"$PM" review history
```

`review due` 會顯示本期識別碼、起始時刻、補做期限、是否已收尾與待回顧數量。它是讀取清單，不會替你接受或發布知識。

預設回顧錨點是本機時間週五 16:00。回顧期以「最近一個已到達的錨點」計算，因此週五時刻到達前新匯入的資料，可能還不屬於目前顯示的那一期。`0 due items` 不代表剛剛匯入失敗，先到 `inbox list` 核對。

補做要沿用原本的週期，不要改成本週。介面可能只顯示 candidate 的短碼；提交 `--item` 時必須使用匯入結果中的完整識別碼。若遺失完整碼，請研發協助從合法讀取介面取回，不要猜或直接改資料庫。

### 步驟 B：本人判讀，必要時請 AI 協助

先看原始紀錄，再問：「當時為什麼這樣決定？」「哪些條件下不適用？」「是否已有更新的證據？」「有沒有需要遮蔽的內容？」

目前這是人工／AI 協助的檢視步驟，不是提醒一出現就自動完成的摘要或訪談。PM 要確認內容；AI 的建議不能代替本人接受，也不能跳過正式記憶的檢查。

可在已允許處理這份資料的 AI 環境中使用這段說明：

> 請協助檢視我提供的工作紀錄，區分原始事實、推測、決策理由與待確認事項。先不要寫入、接受或發布；逐項提出需要我補充的問題，最後整理分類建議與引用的來源。

### 步驟 C：為本期每一筆候選選擇分類

| 指令分類 | 使用時機 |
| --- | --- |
| UNSEEN | 之前尚未看過的新內容。 |
| UNCHANGED | 和已知內容相同，沒有實質變化。 |
| NEW_EVIDENCE | 有補充證據，需要保留新依據。 |
| MATERIALLY_CHANGED | 結論或適用條件有實質改變。 |
| CONTRADICTED | 新內容和先前說法衝突，需要釐清。 |
| NEEDS_ORG_FOLLOWUP | 本人無法回答或欠外部證據，需要後續組織追查。 |

這些是比較／處置分類，不是「正式接受」「自動修正舊知識」或「已開追蹤工單」的同義詞。分類為 NEEDS_ORG_FOLLOWUP 也不代表系統已替你通知同事或建立 Jira。

### 步驟 D：明確指定原週期，送出分類

下面的 `PM_PERIOD` 與 `PM_CANDIDATE` 必須換成實際顯示的值。若該週有多筆，使用多個 `--item`，每筆都要有分類；不能漏選，也不能混入別期資料。

```sh
PM_PERIOD="實際週期，例如 2026-W39"
PM_CANDIDATE="匯入結果的完整 candidate 識別碼"
"$PM" review done --period "$PM_PERIOD" \
  --item "$PM_CANDIDATE=UNSEEN"
"$PM" review history
```

成功時會看到 `COMMITTED` 與 `final_status: NO_PROMOTION`。再以 `review history` 確認同一週已收尾。分類不會把原來的 PROPOSED 候選直接升格成正式知識。

未完成的週不是自動 SKIPPED。確定整期不做，且補做期限已過，才使用下列指令留下明確記錄：

```sh
"$PM" review skip --period "$PM_PERIOD"
```

目前「工作日」的計算以週一至週五為基礎，不內建各地國定假日。假期與特殊排班由人確認，不要假設產品已連結公司行事曆。

## 6. 提醒是可選的，不會替你完成回顧

需研發確認裝置環境並取得使用者同意後，才啟用 macOS 提醒。下列指令會更動本機排程，不是單純查詢。

```sh
"$PM" schedule install
"$PM" schedule status
```

預設在週五 16:00 提醒。通知沒有出現不代表資料遺失；仍可手動執行 `review due`／`review history`。停止提醒使用 `schedule remove`，不等於刪除個人記憶。本文製作與驗證沒有啟用任何真實提醒。

## 7. 遇到問題怎麼處理

| 現象 | 先做什麼 |
| --- | --- |
| 缺 owner／tenant | 請研發檢查安裝身分；兩個值要成對提供。 |
| NEEDS_CANDIDATE_INPUT | 補上適當的 --memory-kind，用同一來源重跑；確認 CANDIDATE_PROPOSED。 |
| 檔案格式或編碼被拒 | 改存 UTF-8 的 .md／.txt，再確認內容完整。 |
| 重匯出現來源／身分衝突 | 保留錯誤碼及原始檔位置，請研發核對；不要修改身分避開。 |
| inbox 有資料，review due 卻是 0 | 先看回顧期的錨點與資料時間，不要重匯直到出現為止。 |
| review done 回報漏項或跨期 | 對照該期完整清單，逐筆分類，移除不屬於該期的項目。 |
| 週期尚未開始或已收尾 | 確認是不是選錯週；不要靠更換週期重複提交。 |
| Claude Code 工具被拒 | 確認安裝與新 session 的初始化；交研發查看錯誤碼。 |
| doctor 出現 FAIL／macOS 阻擋 | 停止匯入，依目前交付包 INSTALL 說明由研發處理。 |

交給研發的資訊以「執行的子指令、錯誤碼、週期、產品版本、已遮蔽的畫面」為主。不要為了排錯直接傳送整份個人資料庫或未遮蔽的工作內容。

## 8. 隱私、共享與目前界線

個人資料預設留在本機；不會因為匯入或回顧完成，就把整份個人 Store 同步到公司。公司共享的目標是未來挑選必要內容、處理敏感資訊，再經既有批准／送審流程。

Local-first 說的是主要儲存位置，不等於所有 AI 推論都在本機。將內容交給 AI 平台處理前，仍須符合公司規則與該平台的設定。本文件沒有實作加密備份、遠端分享或跨平台搬遷工具。

## 9. PM 首次試用的完成標準

使用一個工作週、少量已允許保存的真實紀錄。PM 能說明每筆資料的來源；匯入後能在收件匣找到候選；到期後能為每筆回顧項目分類；收尾後能從歷史確認同一週的狀態。找不到依據或遇到拒絕時，能留下可交研發定位的資訊。

目前未量測省時幅度、問答正確率或採用率；試用時再收集基線與回饋，不預設效益數字。
