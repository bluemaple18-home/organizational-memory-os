# 驗證治理

## 三個狀態分離

`EXECUTED != VERIFIED != ACCEPTED`

Agent 成功執行，只證明做過；Evaluation 跑完，只證明驗過；Reviewer / Policy Acceptance 才決定能否正式採用。

## 三軸

- Complexity：決定處理深度 / model / retrieval depth
- Risk：決定 Verification Requirement
- Uncertainty：決定是否需要更多 Evidence、反證、獨立核對或人工介入

三者不要壓成一個總分。

## Verification Requirement

至少可描述：

- required_source_count
- required_authority
- required_freshness
- counter_evidence_required
- machine_eval_required
- human_review_required
- minimum_eval_coverage

## Verification Status

至少：`PASS / FAIL / PARTIAL / NOT_RUN / STATIC_ONLY`。

20 題只跑 13 題且 13 題全過，仍是 PARTIAL；如果 policy 要求人測而 human eval=NOT_RUN，Acceptance=BLOCKED。

正式原則：

> Missing verification evidence never implies successful verification.

## Evidence chronology

後補證據不能改寫歷史。Answer / Candidate / Evaluation Receipt 保存當時真正使用的 Evidence refs、snapshot time、generated_at、verification_started/completed、accepted_at/by。

## Multi-Agent Evaluation

可以做：Primary Answer、Independent Reviewer、Evidence Hunter、Counter-evidence Reviewer → Compare → Confidence / Conflict。

但 Knowledge SaaS 只定 EvaluationStrategy：role、input scope、expected output、authority、verification。底層可使用不同模型/runtime/provider，不自建 Agent Scheduler / Mailbox / Room。

## Prior Art

`codex-engineering-system-zh-tw` 可吸 Risk≠Complexity、Risk→Verification Requirement、verification honesty、partial/not-run preservation、evidence chronology、execution/verification/acceptance separation；coding workflow/TDD/task routing 不帶入。
