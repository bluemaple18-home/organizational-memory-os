# 公司員工個人記憶標準｜Personal Memory Harness 架構提案

日期：2026-08-30

狀態：

```text
OWNER_SCOPE_CORRECTED
COMPANY_KNOWLEDGE_PREPARATION
DRAFT_DECISION
REVIEW_REQUIRED
NOT_CANONICAL
NO_IMPLEMENTATION_AUTHORIZATION
```

---

## 0. 這次真正要做什麼

本計畫不是：

```text
把完整 AI Core 切出去
為每個員工複製一套 AI Core
為每個員工安裝 Codex / Claude Code / Hermes / DSH
把 AI Core 的開發流程記憶直接變成公司知識庫標準
```

真正目標是：

> 為公司每一位員工定義同一套「個人記憶規格」，讓不同角色的工作 Evidence 先在 PERSONAL 範圍內被整理、查回、修正，再透過 Proposal + Review 升為 Team／Department／Company／Client Knowledge。

AI Core 的完整系統仍留在 AI Core。只抽取其中可泛化的記憶原則、失敗案例與 projection pattern，作為 donor；AI Core 中與 task card、branch、worktree、runtime、review、deploy 對齊的開發專用記憶，不得成為全公司員工的共同 schema。

正式定位：

```text
Organizational Memory OS
= 公司知識與個人記憶產品 Authority

Employee Personal Memory Standard
= 每位員工共用的邏輯 contract、lifecycle、permission 與 promotion 規格

Role / Source Profile
= PM、RD、MD、Sales 等角色的來源與設定差異

AI Core
= Developer-specific implementation donor / advanced source adapter

Agent / Harness / Model
= Optional executor
```

---

# 1. 「每個員工同一套規格」的真正意思

同一套規格代表：

- 同一組 resource identity 與 schema family。
- 同一條 Evidence → WorkRecord → Memory Candidate → Personal Memory lifecycle。
- 同一組 PERSONAL／TEAM／DEPARTMENT／COMPANY／CLIENT Scope。
- 同一套 Permission、Retention、Freshness、Conflict、Correction、Supersession 規則。
- 同一個 Personal → Team／Company Promotion Proposal + Review 邊界。
- 同一種 Recall／Context Pack contract。
- 同一個最低 Safety Floor。

它不代表：

- 每個員工有一模一樣的來源。
- 每個員工都安裝本機 Memory Runtime。
- 每個員工都使用相同 Agent。
- 每個員工都看到相同資料。
- 每個角色都使用同一個 UI View。
- 每個員工都必須採相同 L1–L4 Level。

正確模型：

```text
Same Core Contract
+ Different Role Profile
+ Different Source Adapters
+ Different Capability Level
+ Same Governance Floor
```

例如：

```text
PM
→ Outlook / Teams / Jira / Documents

RD
→ Jira / Git / Documents / Codex or AI Core evidence

MD
→ Documents / Design tools / Teams / Client feedback

Sales
→ CRM / Email / Meetings / Client documents

所有來源
→ 同一 RawEvidenceEnvelope
→ 同一 Personal Memory Standard
```

# 2. 產品中的十個標準零件

## 2.1 Employee Memory Profile

回答：

> 這位員工的個人記憶能力可以接哪些來源、使用哪個 Level、受哪些公司與個人政策約束？

至少包含：

```text
tenant / employee identity
role profile
source connector grants
consent / notice
memory capability level
personal scope policy
sensitivity policy
retention policy
promotion authority
context budget policy
```

Profile 是設定，不是 Memory truth。

## 2.2 Personal Evidence

所有來源先進既有 `RawEvidenceEnvelope` 語意，並帶：

```text
owner employee ref
source identity / version
occurred / observed / received time
payload or artifact ref
ACL snapshot
sensitivity
retention
provenance
```

正式：

```text
Source Event / Document / Message / Runtime Receipt
!= Personal Memory
```

## 2.3 Object Linking

Evidence 可以同時連到：

```text
Project
Client
Order
Jira Issue
Document
Thread
Person
Meeting
Repository
```

Link suggestion 不等於 durable accepted link；accepted link 也不得擴張 permission。

## 2.4 WorkRecord Projection

WorkRecord 回答：

> 這件工作發生了什麼？

它是 Evidence + ObjectLink 的可重建 projection，不是 Personal Memory，也不是 Company Knowledge。

```text
WorkRecord
!= Personal Memory
!= Canonical Knowledge
```

## 2.5 Personal Memory Candidate

從 Evidence／WorkRecord 萃取「可能值得長期保留」的內容。

Phase-1 memory kinds：

```text
WORK_PREFERENCE
WORKING_STYLE
DOMAIN_FACT
DEFINITION
RULE
DECISION
LESSON
PROCEDURE
PROJECT_CONTEXT
RELATIONSHIP_CONTEXT
LONG_LIVED_CONSTRAINT
```

預設不升長期記憶：

```text
current task status
one-off command output
transient open loop
temporary branch / worktree state
runtime completed message
unverified model suggestion
短期排程與一次性提醒
```

## 2.6 Personal Memory Governance

每筆 Candidate 必須可表達：

```text
source support
scope
sensitivity
applicability
validity / freshness
confidence
conflict
supersession
correction
retention / deletion
verification requirement
acceptance status
```

核心：

```text
Captured != Remembered
Candidate != Accepted Personal Memory
Model confidence != Verification
```

## 2.7 Personal Memory Record

Personal Memory Record 是在 PERSONAL 範圍內被接受、可正式回憶使用的記憶。

它至少包含：

```text
memory identity
employee owner
memory kind
statement / structured content
applicability
validity interval
evidence refs / source anchors
provenance
verification / acceptance
sensitivity / ACL
freshness / review due
conflict refs
supersedes / superseded_by
retention state
```

正式：

```text
Personal Canonical Memory
= canonical only inside PERSONAL scope
!= Company Canonical Knowledge
```

## 2.8 Recall / Context Pack

AI 或員工查詢時，不應直接載入全部個人資料。

```text
Intent
→ Identity / Permission
→ Applicable Personal Memory
→ Freshness / Authority
→ Context Budget
→ Bounded MemoryContextPack
```

MemoryContextPack 至少回傳：

```text
selected memory refs
source refs
applicability
freshness
sensitivity result
gaps / omitted reason
context budget usage
```

## 2.9 Correction / Supersession

員工說「這個偏好改了」或「這條記憶錯了」時：

```text
User Correction
→ New Evidence
→ Correction Proposal
→ Verify / Accept
→ Supersede or Amend
```

禁止直接覆寫並刪掉歷史 provenance。

## 2.10 Promotion Proposal

Personal Memory 可以提出：

```text
TEAM
DEPARTMENT
COMPANY
CLIENT
```

的 Knowledge Candidate，但不能直接升格。

```text
Personal Memory / Candidate
→ Promotion Proposal
→ Permission / Scope Check
→ Evidence Support
→ Verification
→ Human / Policy Review
→ Canonical Single Writer
→ Shared Canonical Knowledge
```

Scope promotion 不是 copy，也不是把私人內容原封不動公開。

# 3. 個人記憶的 Privacy / Ownership 必須分軸

公司環境中的「PERSONAL」不能只靠名稱判定權限。

規格必須支援至少三種 policy mode：

```text
EMPLOYEE_PRIVATE
= 員工私人、公司不得因管理員身分直接讀取

COMPANY_MANAGED_PERSONAL
= 公司提供並依法／依政策管理的個人工作記憶空間

SHARED_WORK_CONTEXT
= 已明確屬 Team／Department／Client 的工作上下文
```

這三種模式可能共用同一 schema，但：

- 可見者不同。
- retention 不同。
- export / delete 權利不同。
- promotion authority 不同。
- 離職交接規則不同。

在這個 owner／privacy policy 未封之前，禁止把「每位員工都有個人記憶」解讀成「公司可以搜尋所有人的個人記憶」。

# 4. L1–L4 與員工標準的關係

正式 Level 維持：

```text
L1 基礎
L2 自動化
L3 智慧化
L4 自治化
```

所有 Level 使用同一份 contract；差別只在 automation depth。

## L1 基礎

- 員工手動上傳／標記 Evidence。
- 系統提出 Candidate。
- 主要由本人確認。
- 基本 Recall + Citation。

## L2 自動化

- Outlook／Teams／Jira／文件等來源自動 Evidence ingest。
- deterministic duplicate、version、ACL、retention處理。
- 自動產生待確認 Candidate。

## L3 智慧化

- Cross-source Object Linking。
- WorkRecord correlation。
- Conflict／Freshness／Missing Evidence提示。
- Context-aware Recall。
- Promotion suggestion。

## L4 自治化

- 持續監測過期、衝突與缺口。
- 主動提出 Correction／Promotion Proposal。
- 主動重建 projection與回歸評測。
- 仍不得跳過 Scope Authority、Verification、Acceptance與Canonical Writer。

「每個員工同一套規格」不等於每個員工固定 L2；Default Level 是產品設定與政策決策。

# 5. AI Core 應如何被吸收

AI Core 不是每位員工的產品基線。

## 5.1 可以吸收

- Evidence → distilled memory 的失敗案例。
- preference／working style／lesson／decision／procedure分類經驗。
- correction、supersession、provenance與 startup context projection pattern。
- bounded recall、context budget、freshness與 verification honesty。
- Founder Vault 作 human-readable projection 的經驗。

## 5.2 不可直接吸收成員工共用標準

- task card status。
- branch／worktree／reservation。
- runtime session／thread。
- provider、model routing、agent team。
- code review／merge／deploy state。
- 開發流程專用的 canonical workflow rules。
- `.memory` 或 `.founder-vault` 的實體檔案布局。

## 5.3 AI Core 的正確產品位置

```text
AI Core
→ Developer Role Source Adapter / Advanced Memory Profile
→ 同一 Employee Personal Memory Standard
```

例如：

```text
AI Core accepted lesson
→ Personal Evidence
→ LESSON Candidate

AI Core task RUNNING
→ Work Context only
→ 不升長期 Personal Memory

AI Core accepted architecture decision
→ DECISION Candidate
→ PERSONAL 或 Promotion Proposal
```

AI Core 只是其中一種進階來源，不是 schema authority。

# 6. 部署模型

普通員工不需要本機 AI Core 或獨立 Memory Runtime。

建議產品形狀：

```text
Central Company / SaaS Memory Services
├─ Source Adapters
├─ Personal Evidence Store / references
├─ Object / WorkRecord projections
├─ Candidate distillation workers
├─ Personal Memory governance
├─ Permission-aware recall
└─ Promotion workflow

Employee
└─ 使用 Outlook / Teams / Jira / Docs / Web / Existing UI
```

Agent、LLM、Hermes、DSH 等都只是後端可替換 executor。

同一規格可以部署成：

- SaaS central service。
- 私有雲。
- 地端企業環境。
- 特定角色的 local adapter。

但不得因部署不同而產生不同 Knowledge lifecycle。

# 8. Role Profile 只能擴來源與設定，不能改核心語意

Role Profile 可以決定：

```text
sources
memory kind suggestions
sensitivity defaults
retention defaults
review requirements
context pack priorities
```

例如：

```text
PM_PROFILE
RD_PROFILE
MD_PROFILE
SALES_PROFILE
OPERATIONS_PROFILE
```

但 Role Profile 不得：

- 新增第二套 Evidence identity。
- 放寬公司 Managed Policy Floor。
- 跳過 PERSONAL → COMPANY Review。
- 改變 Candidate != Canonical。
- 把自己的 folder taxonomy變成全平台 schema。

Extension 必須 namespaced。

# 10. 正式 Backlog 建議

## `EMEM-00` — Employee Personal Memory Scope / Ownership Contract

先封：

- PERSONAL 的三種 ownership／privacy mode。
- 員工、公司、主管、Reviewer 的權限。
- 離職、移轉、export、delete、legal hold。
- 同一核心規格與 Role Profile 邊界。

## `EMEM-01` — Personal Memory Candidate / Record Schema

封：

- memory kinds。
- support／provenance。
- validity／freshness。
- correction／supersession。
- verification／acceptance。

## `EMEM-02` — Personal Evidence Profile

把文件、Jira、Teams／Outlook與進階 Agent sources映射到同一 RawEvidence contract。

## `EMEM-03` — Recall / MemoryContextPack

封 permission、applicability、freshness、context budget、citation與gap notice。

## `EMEM-04` — Correction / Supersession

封 correction evidence、proposal、verification、acceptance 與 amend／invalidate／supersede，不允許原地覆寫舊 provenance。

## `EMEM-05` — Promotion Proposal

封 PERSONAL → TEAM／DEPARTMENT／COMPANY／CLIENT 的 proposal、review、redaction與single-writer path。

## `EMEM-06` — Product Department Pilot

只做一個小型 vertical slice，不一次接全公司全來源。

## `EMEM-07` — Role Profiles

在核心 contract穩定後才定 PM／RD／MD／Sales presets。

## `EMEM-08` — AI Core Developer Adapter

AI Core只作 developer-specific source／consumer adapter；不成為所有員工的依賴。

# 11. Hard Stops

禁止：

- 把完整 AI Core 複製成每位員工的 Personal AI Core。
- 以 `.memory`、`.founder-vault` folder作公司標準 schema。
- 把 task／branch／worktree／runtime completion預設升成長期記憶。
- 要求一般員工安裝 Codex／Claude／Hermes／DSH。
- 每個 Role 建一套不同 lifecycle。
- Personal Memory直接寫 Company Canonical Knowledge。
- 公司先搜尋所有 Personal Memory，再叫 LLM不要洩漏。
- 以 model confidence自動接受或跨 scope promotion。
- Correction直接覆寫舊記憶與provenance。
- 把個人記憶和 WorkRecord混成同一個物件。
- 在 ownership／privacy policy未封前大量自動擷取員工資料。

---

# 12. 最終裁決

正確的產品不是：

```text
AI Core Lite for every employee
```

而是：

```text
One Employee Personal Memory Standard
for every employee

+ role-specific sources
+ centrally managed or on-prem services
+ personal-scope governance
+ permission-aware recall
+ reviewed promotion into organizational knowledge
```

AI Core的記憶能力只提供 donor與developer profile；公司員工共同規格必須保持工具中立、角色中立、runtime中立。
