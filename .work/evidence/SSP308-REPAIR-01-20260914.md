### F-02：`SessionStart`／`Stop` 的粒度不安全，實測確認

用 `WebFetch` 分別查證兩件事：

1. **`Stop` 是 per-turn cadence**（「When Claude finishes responding」，
   每個 turn 結束都觸發），不是 per-Work-Record。
2. **`SessionStart` 會在同一個 session 內重複觸發**——文件原文：
   「Later in a running session: after `/clear` or a compaction,
   `SessionStart` fires again with the servers already available」。

依 `ai-task-card-record.yaml` 的 `allowed_status_transitions`：

```
OPEN:      [BLOCKED, IN_REVIEW, CANCELLED]   ← 沒有 OPEN 自迴圈
IN_REVIEW: [OPEN, DONE, CANCELLED]           ← 沒有 IN_REVIEW 自迴圈
```

所以：第二個 turn 的 `Stop → submit_review` 會嘗試 `IN_REVIEW → IN_REVIEW`
（不存在）；若 compaction 發生在第一個 `Stop` 之前，重複的
`SessionStart → start` 會嘗試 `OPEN → OPEN`（不存在）。兩者都是**正常多
turn 使用會發生的情況**，不是邊緣案例。

我也查了 `TaskCreated`／`TaskCompleted`（名稱上像任務邊界），文件只寫
「透過 `TaskCreate` 建立／標記完成」，**沒有確認**是否對應 AIWR 的頂層
Work Record 邊界，還是 Claude Code 自己的內部任務／佇列機制——不夠確定，
不猜。

**修法**：`lifecycle_event_map` 本輪清空，33 個事件全部分類為
`non_lifecycle_event_types`。這是本契約自己「不猜」原則的誠實延伸——
沒有任何 hook 名稱有文件確認的「每個 Work Record 最多一次」保證，而本
Adapter 依 `hard_stops` 是無狀態純函式，無法靠事件名稱本身區分首次與重複。
把實際映射決策升級為 runtime probe 延後卡的**硬性前置**（見
`.work/CARD-SSP308-RUNTIME-PROBE-BACKLOG-20260914.md` 的 escalated 欄位）。

### F-03：完整性檢查原本是同檔互比

`spec.dig("documented_native_vocabulary", "hook_events")` 讀的跟
`classified`（`lifecycle_map.keys + non_lifecycle`）都來自同一份 YAML，
互比證明不了跟真實文件的關係——這正是 F-01 能直接發生的原因。

修法：改為對照 `規格/v0.1/fixtures/claude-code-hook-events-doc-snapshot.json`
（獨立檔案，帶 `source_url`／`captured_at`）。新增結構斷言要求該檔必須
存在這兩個出處欄位。

## 因 F-02 而產生的死碼，主動清理

`lifecycle_map` 清空後，`claude_code_mapping_failure` 裡「`mapped_to` 是否
等於 declared map entry」那一段永遠不可達（`lifecycle_map.key?` 對空 Hash
恆為 false，前一行永遠先回傳）。移除該段與對應的
`CLAUDE_CODE_MAPPING_TARGET_MISMATCH` 宣告，並在原處留註解說明：**這是
資料驅動的暫時不可達，不是邏輯上永遠不可達**——map 一旦有條目就會重新
可達，屆時依當時的 guard parity 補回。因為 `error_contract` 綁定已經走
AST 模組（沿用 SSP-302／SSP-307），移除這條 return 後，宣告集合自動同步
縮小，不需要手動調整任何清單。

## 主動揭露：懷疑已合併的 SSP-307 有同一類問題（未在本卡修）

`task_started → start`／`task_complete → submit_review` 是 SSP-307
（`ACCEPTED_GO @ 32b3f82`）的既有映射。SSP-307 的真實 runtime 資料顯示
`task_started`／`task_complete` 平均每 session 出現約 11.6 次（9529／9392
次除以 818 個 session）——這強烈暗示它們也是 per-turn cadence，不是
per-Work-Record 一次。若屬實，第二個 turn 的 `task_complete` 一樣會嘗試
`IN_REVIEW → IN_REVIEW`。

**這是本卡研究過程中自然浮現的懷疑，不是本卡的修復範圍。** SSP-307 是
已經 Owner 接受、合併進 `main` 的獨立 review line，本卡不擅自回頭改它。
已在對話中直接回報給 Owner，由 Owner 決定是否開新卡處理。
