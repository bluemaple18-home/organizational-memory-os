## 被修的 finding

`SSP291-F-01`（P1）：准入值驗證不完整，錯型別 reference 與空 scope 匹配仍可放行。

reviewer 從合法正例出發的單欄重播，以下四項 evaluator 均回傳 `nil`（允許）：

| 單欄修改 | 應為 | 實際 |
| --- | --- | --- |
| `consent_or_notice_ref = false` | deny | allow |
| Jira grant 的 `grant_ref = false` | deny | allow |
| `retention_policy_ref = false` | deny | allow |
| `consent_or_notice_ref = "   "` | deny | allow |

另兩種「兩邊都缺值」互相匹配：

- `capture_scope.containers` 含 `null`、capture 不帶 `container` → `include?(nil)` 成立 → allow
- `capture_scope.source_instance_ids` 含 `null`、capture 與 projected identity 都不帶
  `source_instance_id` → `include?(nil)` 與 `nil == nil` 皆成立 → allow

根因：三處 reference 檢查與欄位存在性檢查共用 `present?`，而
`present?` 只排除 `nil` 與 `empty?`，因此 `false`、`0`、純空白字串、
非空 Array／Hash 都被當成「存在」。它從來沒有驗證那個值是不是一個 reference。
scope 與 identity 比較則是先比較、後（不）驗型別。

## 修法（reviewer 指定的定點修法）

1. 本檔新增 `admission_value?`：**非空白 String**。不造 URI scheme、不連外解析。
   涵蓋 consent／notice、grant_ref，以及上游要求的四個 policy reference。
2. `source_policy` 的兩個容器欄位（`connector_grants` / `capture_scope`）
   以本卡自有的 `ADMISSION_CONTAINER_TYPES` 驗型別且非空。
   這是本卡的准入形狀，不是上游列舉，故不違反「零列舉重述」。
3. `within_capture_scope?`：先要求 scope 兩個清單是 Array、且 capture 帶有合法識別值，
   再做成員判斷。`null` 不得與缺失欄位構成合法匹配。
4. projected identity：先驗 `source_system` / `source_instance_id` 為合法識別值，
   再做相等比較。
5. **錯誤碼集合維持 16 個不變**，順序不變。缺值一律落在原本語意正確的碼上
   （profile 欄位 → `EPROFILE_PROFILE_FIELD_MISSING`；
   capture 識別值 → `EPROFILE_OUTSIDE_CAPTURE_SCOPE`；
   projected → `EPROFILE_ADAPTER_MAPPING_MISMATCH` / `EPROFILE_PROJECTED_IDENTITY_INCONSISTENT`）。
6. 契約新增 `admission_value_constraints` 區塊說明上述約束，並由 validator 斷言其存在。
