## 4. 特別請看的點

1. **Runtime evidence 的來源與可信度**。`規格/v0.1/codex-native-adapter.yaml`
   的 `measured_native_vocabulary` 宣稱：對本機 `~/.codex/sessions/**/*.jsonl`
   **全量掃描**（818 個 session，不是抽樣）取得的事件類型分布。這是我在
   Owner 明確授權後讀取的，只萃取 `event_msg.payload.type`（受控 discriminator
   欄位）與出現次數，**沒有讀取或儲存任何訊息內容、工具輸出或檔案內容**。
   `規格/v0.1/fixtures/codex-native-adapter-runtime-sample.json` 是這份萃取的
   凍結快照，reviewer 不需要本機有 Codex session 檔就能驗證分類完整性。
   請檢查這份 evidence 除了信我的話之外，還有沒有別的可重現路徑——
   目前答案是沒有，這是本卡誠實的取捨（見 §7 已知取捨第 3 點）。

2. **`turn_aborted → cancel` 是設計判斷，不是推導出來的必然結果。**
   契約 `lifecycle_event_map.design_note` 寫明了理由：一個未完成就結束的
   turn，語意上比較接近「取消」而非「封鎖」（block 隱含仍待處理／可恢復）。
   104 次真實觀測，非零但稀有。**請直接挑戰這個判斷**——如果你認為更接近
   `block`，這是可討論的設計點。

3. **`block`／`unblock`／`submit_review` 永久缺席於 `lifecycle_event_map`，
   這是刻意的，不是遺漏。** Codex 原生 session 事件裡沒有任何東西對應這三個
   AIWR 構造。全量掃描的 10 種事件類型裡，沒有一種語意接近它們。

4. **一個我自己發現、修正、並留下痕跡的死碼**。`CODEX_MAP_TARGET_UNKNOWN`
   原本設計成「run 帶了一個指向不存在 lifecycle key 的 `mapped_to`」該回傳
   的碼，但實測發現 `declared_target` 一律從已通過結構斷言的契約本身讀出，
   run 層級輸入永遠無法觸發這條 guard——我寫負例去踩它，得到的是
   `CODEX_MAPPING_TARGET_MISMATCH` 而非預期碼。依 SSP-291 對
   `EPROFILE_ADAPTER_MAPPING_NOT_BOUND` 的同一取捨，刪除死碼，改由既有結構
   斷言承擔。**請判斷這個取捨對不對**；如果你認為執行期仍該留防禦，那是 finding。

5. **guard parity 過程中抓到 8 個真缺口，已補負例，請重播確認**。
   同一個 machine failure code 被多條 guard 共用（例如三種不同的
   forbidden-authority 欄位都回傳 `CODEX_EXCEEDS_AUTHORITY`），只有其中一條
   最初被 fixture 踩到，其餘 7 條是死分支。全部補齊後轉全紅，見 §5。

6. **一個型別 guard 的偽陰性，換了反例才抓到**。`is_a?(Hash)` 的 guard 一開始
   用字串 `"not-an-object"` 當反例測，因為 Ruby 的 `String#[]` 對字串參數是
   substring 查詢、不拋例外，下一條 guard 用同一個 code 兜底，parity 顯示
   GREEN(bad)——但這是兩條 guard 剛好對同一輸入給出相同結論，不是真漏洞。
   換成 `nil` 反例（`nil["disable_switch"]` 會拋 `NoMethodError`）才讓
   型別 guard 本身變成不可或缺。

## 6. 邊界

本卡**不做**、也不接受以「更完整」為理由加進來的東西：

- Codex 原生事件的即時訂閱／connector／event bus／always-on 監聽器。
- AIWR `complete`、Personal Memory acceptance、canonical writer authority。
- 重定義 `ai-task-card-record.yaml` 或 `ai-work-record-hook.yaml`。
- registry / FSM / DB / writer。
- 讀取或儲存任何 session 訊息內容、工具輸出、檔案內容。

若 finding 需要跨過以上任一條，那是 Owner 決策，不是本卡的 repair。

## 7. 已知取捨

1. `turn_aborted → cancel` 是判斷，不是強制對應（見 §4-2）。
2. `block`／`unblock`／`submit_review` 永久缺席，刻意的（見 §4-3）。
3. **Runtime probe 的證據是一次性凍結快照，不是即時連線。** 2026-09-14 對

   長期維護需要刷新流程，本卡不處理（屬 `SSP-309`／`SSP-310` 範疇）。
