## 6. 指定加壓面

1. **trace 只驗頭尾與集合成員,未驗中段 transition 合法性**：evaluator 不 replay
   `allowed_status_transitions`（那是 SSP-299 / SSP-302 的職責）。確認「start → cancel → complete」
   這種頭尾合法但中段非法的序列是否應被本卡擋,還是交由上游 Loop/Skill 契約。（傾向 P2/P3。）
2. **`manager_view` 欄位值型別未驗**：`objective` / `blockers` / `acceptance_summary` 只要
   key 在就過,沒驗是非空字串。一個 `blockers: null` 的 view 會通過(除非 reconstruction 檢 `status`)。
   是否該要求五欄皆非空?
3. **`work_records` 為選填**：`run["work_records"].to_a` —— 缺 `work_records` 的 run 直接跳過
   memory 升格閘門。這對「這次任務沒有任何 WorkRecord」是正確的,但確認沒有讓「有 WorkRecord
   卻不列進 `work_records`」的 run 溜過(本卡無法知道 run 隱藏了 record —— 屬契約邊界,不是漏洞)。
3. **`E2E_STATUS_UNMAPPED` 只對映 `complete`/`cancel`**：`FAILED` / `BLOCKED` /
   `HUMAN_INTERVENTION` 三個 manager status 沒有對應的終止 event（trace 只收在 complete/cancel）。
   一個 trace 收在 `complete` 但 `final_status: FAILED` 會被擋（好），但「任務其實失敗了卻用
   `complete` 收 trace」本卡無法辨識。是否該擴充 terminal_events 或要求 FAILED/BLOCKED 對應
   `cancel` 收尾 + blockers 非空?（傾向 backlog。）
4. **`sensitive_content_copied` 是 run 自報旗標**：本卡靠 run 誠實回報有沒有複製敏感內容。
   validator 另擋 `raw_work_body` 具名欄位與非 allowed 欄位,但無法掃描 `objective` /
   `acceptance_summary` 字串內容是否夾帶敏感字。這是否為可接受的契約邊界(內容掃描非本層職責)?
5. **`reconstructable_from_jira` 亦為 run 自報**：evaluator 另檢 `status` / `evidence_links`
   非空作為客觀佐證。確認這兩項足以作為「可重現」的最小可驗條件。
6. **duplicate JSON / YAML key**：4 個新檔經 `StrictJsonObject` / `assert_unique_yaml_mapping_keys`（lib）解析。
