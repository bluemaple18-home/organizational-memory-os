## 6. 指定加壓面

1. **冪等定義是否夠嚴**：`hook_capture_failure` 以 `raw.uniq { |e| e["event_key"] }` 去重並要求
   `emitted_events` 完全等於去重後 `event` 序列。若同一 `event_key` 帶不同 `event` 值（矛盾事件），
   目前 `uniq` 只保留第一筆 —— 這是否是預期？是否該加「同 key 不同 event」的拒絕碼？
2. **ordering 依賴 `event_key` 出現順序**：`raw_events` 陣列順序即事件順序，沒有用 `occurred_at`
   排序。若 runtime 亂序送入，`HOOK_BATCH_MUST_START` / `HOOK_ILLEGAL_TRANSITION` 會誤判。
   契約是否該要求 Hook 先按 `occurred_at` 排序、或明確聲明「呼叫端保證有序」？
3. **`replay_transition_failure` 對未知 event 會 `KeyError`**：實務上一定先被 `HOOK_EVENT_NOT_ALLOWED`
   攔下（與 skill validator `replay_lifecycle` 同款防禦順序），但若加壓面 1/2 的重構動到順序，
   確認這條不會變成未捕捉例外。
4. **`HOOK_OUTPUT_NOT_SKILL_INPUT` 覆蓋面**：目前只檢「空批次」。skill `lifecycle_events_rule`
   另含「first is start」「每個 event 是 lifecycle key」——這兩條在 hook evaluator 由
   `HOOK_BATCH_MUST_START` 與 `HOOK_EVENT_NOT_ALLOWED` 分別覆蓋。確認沒有 skill 會拒、hook 會放的縫。
5. **停用狀態的 authority 檢查被略過**：`disabled == true` 時 evaluator 直接 return，不檢查
   `performs_memory_acceptance` / forbidden batch fields。停用理應發空批次所以無害，但確認
   `HOOK_DISABLED_STILL_EMITTING` 的「空」定義（`emitted_events.empty? && batch empty`）沒有讓
   一個「lifecycle_events 空但夾帶 `personal_acceptance_ref`」的畸形 payload 溜過。
6. **`present?` 語意**：`side_effect` 欄位用 `present?`（來自 `scripts/lib/omos_contract_helpers.rb`，
   `nil` 或空字串/空集合為 not present）。確認 `failure_state: ""` 會被 `HOOK_ROLLBACK_SIDE_EFFECT_UNSPECIFIED` 擋。
7. **duplicate JSON / YAML key**：三個新檔經 `StrictJsonObject` / `assert_unique_yaml_mapping_keys`
   （lib）解析；確認 fixtures 無重複 key 繞過。
