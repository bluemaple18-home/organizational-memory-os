## 4. 特別請看的點

1. **綁定是不是真的執行期讀取，還是抄了一份。** 這是本卡的核心主張。
   `upstream_bindings` / `phase_gate` / `adapter_mapping_binding` 全部只存 path，
   validator 當場從上游 YAML 讀值。契約內另有一條斷言，禁止把 adapter 的
   `source_system` 值複寫進本契約（否則「抄一份就永遠相等」）。
   請直接改上游的值，看 gate 是否轉紅。

2. **判斷順序是否可被繞過。** `evaluation_order` 有 12 段，evaluator 依同一順序短路回傳。
   請找「先過了較寬鬆的檢查、就繞過較嚴格的檢查」的路徑。特別是：
   role 准入與 phase gate 誰先誰後、consent 檢查為何刻意從欄位存在性檢查中拆出來後移。

3. **`EPROFILE_ADAPTER_MAPPING_NOT_BOUND` 被我刪掉了。** 理由：phase gate 斷言
   `adapters.keys == phase_1_pilot.first_sources`，任何能走到那一步的來源必然已綁定，
   該分支不可達。我選擇刪除死分支、由結構斷言承擔，而不是留一個永遠不會被負例覆蓋的 code。
   請判斷這個取捨對不對；如果你認為執行期仍應保留防禦，那是 finding。

4. **`error_contract` 的綁定方式。** SSP-302 的 TIGHTEN-F-01 指出：由同一隻手寫的
   兩份清單互比，證明不了 evaluator。本卡改成掃描 `evidence_profile_failure` 函式本體的
   `return "<CODE>"` 字面量，與 YAML `error_contract` keys 取等。
   **請直接改一個 return 的字串，確認 gate 轉紅**（我跑過是 RED，但請自行重現）。

5. **`capture_scope` 的成員判斷是扁平的。** `source_instance_ids` + `containers` 兩個清單
   做 `include?`，不做前綴 / 階層 / glob。我的判斷是階層語意屬 connector 範疇（本卡明確排除）。
   如果你認為扁平清單在真實 Jira project / Drive 目錄下不可用，請說。

6. **上游本身的不一致，我沒有修。** `role_profiles` 列了 `CLIENT_FEEDBACK`、`CRM_ENTITY`、
   `CLIENT_DOCUMENT`，但 `source_profiles` 目錄裡沒有這三個。本契約的順序讓它們一律落在
   `EPROFILE_SOURCE_NOT_DECLARED`（fail-closed、方向正確），但這是上游 bug。
   我不改上游是為了不擴大 blast radius。請判斷這是否應該是本卡的責任。

7. **單向綁定。** 我沒有把 `PersonalEvidenceProfile` 加回上游
