## 6. 指定加壓面

1. **「最終缺口」取樣**：evaluator 用 `iterations.last["remaining_gaps"]` 當最終狀態。若某輪
   `remaining_gaps` 非單調收斂（中間輪比最後輪多）、或最後一輪 `remaining_gaps` 缺欄位，
   是否有縫讓「其實還有未處理缺口」的 run 過關？契約是否該要求最後一輪 remaining_gaps 為
   全體未解缺口的 superset？
2. **`filled_fields` 未要求對應到真的缺口**：evaluator 只檢查 `filled_fields ⊆ fillable_fields`，
   沒檢查「補的欄位確實在先前輪的 `remaining_gaps` 內」。Loop 可宣稱補了一個本來就在的欄位。
   這是否為可接受的鬆綁(契約層只保證不擴張 scope)，還是 P2？
3. **`outcome == CLOSED` 未要求 `remaining_gaps` 為空**：目前 `CLOSED` 只要 terminal_condition
   ∈ {ALL_REQUIRED_PRESENT, MAX_ITERATIONS_REACHED} 即可。`MAX_ITERATIONS_REACHED` + `CLOSED` +
   仍有非人類決策/非 unfixable 的普通缺口 → 會過。這是否是預期(達上限就收，普通缺口留給人)?
   還是該要求 `ALL_REQUIRED_PRESENT` 時 remaining_gaps 必須空?
4. **human-decision 與 unfixable 同時存在**：一個 gap `requires_human_decision:true`、另一個
   `auto_fixable:false`。evaluator 先判 human（要 BLOCKED），再判 unfixable（要 FAILED_LOUD）——
   兩者互斥，run 只能有一個 outcome。確認這個優先序(human 先)是契約想要的。
5. **`timeout_seconds` 只檢查正整數,沒有上界**：是否需要契約層的合理上界(避免「1e9 秒」等於無界)?
   目前判 P3 / backlog 傾向,想聽 reviewer 意見。
6. **duplicate JSON / YAML key**：4 個新檔經 `StrictJsonObject` / `assert_unique_yaml_mapping_keys`
   （lib）解析。
